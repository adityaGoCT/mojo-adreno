# Mojo and MAX on Adreno: speaker notes

## 1. Mojo and MAX on a phone GPU

Welcome. This talk is the story of one experiment: can Mojo, and Modular’s MAX platform built on it, run on a phone GPU? Mojo officially targets NVIDIA, AMD and Apple GPUs. Our phone, a moto g stylus 5G from 2024, has a Qualcomm Adreno 710, which speaks only Vulkan and OpenCL. We went at it in two ways. First we borrowed the LLVM IR that Mojo emits for an AMD GPU and rewrote it into Vulkan shaders and OpenCL C ourselves. That got eight test kernels and a full Llama 3.2 1B running. Then, partway through, Modular open-sourced the Mojo compiler, so we built it from source and added a real Adreno target to it, and ran the same kernels and the same Llama through that. I will close with the honest answer to the question everyone asks next: does that mean MAX itself now runs on the phone? Every number in this deck was measured on the device; nothing is an estimate.

## 2. THE QUESTION

Here is the question we started with. Mojo compiles GPU kernels for NVIDIA, AMD and Apple, and MAX, Modular’s inference platform, runs models on those same GPUs. Phones are different: Qualcomm’s Adreno GPUs are reached through Vulkan compute shaders, written in SPIR-V, or through OpenCL. Neither is a Mojo target. Our test device is a mid-range phone, a moto g stylus 5G from 2024, with an Adreno 710. We used three drivers on it: Qualcomm’s own Vulkan 1.1 driver that ships with the phone, Mesa’s open-source Turnip driver, which supports Vulkan 1.4 and which we side-load without root, and Qualcomm’s OpenCL 3.0. The drivers matter a lot later, because they disagree on what is fast and, in two places, on what is correct. We started with Mojo 1.2 and MAX 26.7 exactly as shipped.

## 3. Five acts

The talk follows five acts. In act one, Mojo had no route to this GPU, so we took the LLVM IR that Mojo emits for an AMD GPU and rewrote it, with about a thousand lines of Python, into Vulkan SPIR-V and OpenCL C. Act two is the real test: Llama 3.2 1B, every decode step on the phone’s GPU, checked token by token against PyTorch. Act three is MAX: what it is, how it compiles a vision model, and why it had no road to the phone. In act four the ground moved: Modular open-sourced the Mojo compiler, so we built it ourselves and gave it a proper Adreno target, and the retargeter went away. Act five answers whether that makes MAX itself portable. Colour coding throughout: orange is tooling we wrote around Mojo, blue is Mojo’s own compiler, extended from the inside.

## 4. Act 1 · Borrow Mojo’s LLVM IR

Act one. Mojo 1.2 cannot target this GPU, but it can write out the LLVM IR of a GPU kernel. So we compiled each kernel for an AMD GPU, gfx90a, and kept the IR. We picked AMD on purpose: Mojo resolves the warp size per target at compile time, and AMD’s 64-lane warps match the Adreno’s 64-lane subgroups, so code that depends on WARP_SIZE keeps working. That IR goes through LLVM’s optimizer with the target stripped, then through mojo2vk, a 598-line Python retargeter we wrote, and finally through LLVM 22’s SPIR-V backend to produce a Vulkan compute shader. Qualcomm’s OpenCL driver does not accept SPIR-V, so a second retargeter, mojo2cl, writes OpenCL C from the same IR and the driver compiles it on the phone. On the device, a small C program loads the shader, binds buffers, dispatches, and checks every single output element against a reference.

## 5. What the retargeter rewrites

This table is the whole job of the retargeter. Mojo kernels look like CUDA: they take raw pointers and scalars as arguments and compute addresses freely. A Vulkan compute shader takes no arguments at all. Memory arrives through descriptor-bound storage buffers, and SPIR-V for Vulkan uses logical addressing, which means a shader cannot do arithmetic on pointers. So every pointer argument becomes a storage buffer at a fixed binding, every scalar argument becomes a 64-bit slot in a small parameter buffer, and every address is tracked through its chain of getelementptr instructions as a pair: which buffer, and which element index. At each load or store we rebuild a typed access into that buffer. AMD-specific pieces get translated too: thread and block registers become SPIR-V builtins, AMD’s lane-permute instructions become subgroup shuffles, the barrier becomes OpControlBarrier, and for Qualcomm’s stock driver, which has no 64-bit integers, all index math is narrowed to 32 bits.

## 6. Bugs in the way, and how we got around them

Most of the effort in act one went into bugs that were not in Mojo at all. Three were in LLVM 22’s SPIR-V backend: it emits barrier memory semantics that Vulkan forbids, so we patch the binary; loop strength reduction turns indices into pointer increments that crash its pointer legalizer, so we turn that pass off; and an if-elif chain produced control flow that is not properly structured, so we rewrote that kernel as a single if-else. Three more were in Qualcomm’s stock driver. It lays out two 16-bit shared arrays on top of each other, so we pad them. It does not bring a subgroup back together after a loop where lanes ran different trip counts, so shuffles read inactive lanes and Llama’s attention came out 64 times off until we made loops uniform and moved reductions into shared memory. And it has no 64-bit integers, while Mojo’s Int is 64-bit, so all index math is narrowed. Every one of these either crashed or silently produced wrong numbers, which is why every kernel run checks every output.

## 7. Eight kernels pass on all three drivers

With those fixes, all eight test kernels pass on all three drivers: vector add, vectorized vec4 loads, a warp sum, a block sum through shared memory, and four matrix multiplies. The SGEMM ladder is worth a look. The naive kernel is slowest on Turnip but surprisingly fastest on the stock driver, because Qualcomm’s compiler handles that simple loop well and the shared-memory versions poorly. Register tiling, where each thread computes an eight by eight block of outputs, is the big jump everywhere: 32.5 milliseconds on Turnip, about 66 GFLOP/s for a 1024-cubed multiply, and about twice that time on the stock Vulkan driver and on OpenCL. One lesson from tuning: the two drivers want different memory access shapes, Mesa contiguous chunks and Qualcomm strided ones, so a single kernel is never best on both.

## 8. Act 2 · Llama 3.2 1B on the phone’s GPU

Kernels that pass tests are one thing; act two asks whether the pipeline holds up for a real model. We took the official Llama 3.2 1B Instruct weights and exported them to fp16, fusing the query, key and value projections into one matrix and the gate and up projections into another, which leaves 2.47 gigabytes in 103 tensors. The stock driver will not bind a buffer larger than 128 megabytes, so the token-embedding table is split into four chunks. Decode is seven Mojo kernels, 219 lines in total; the matrix-vector products carry almost all of the memory traffic and end with a warp sum. Instead of MAX, which cannot run on Android, a 398-line C program drives Vulkan: it uploads the weights once, builds the pipelines, and records 150 dispatches for every token. On the Mac, the same prompt runs through PyTorch in fp32, and we compare every generated token and the logits after the prompt.

## 9. LLAMA 3.2 1B, DECODED ON THE ADRENO 710

And it works. Asked to explain in two sentences why the sky is blue, the phone generates 48 tokens, and all 48 are the same tokens PyTorch produces, which is a much stronger check than plausible-looking text. The logits after the prompt differ from PyTorch’s by at most 6.2 times ten to the minus five. Decode runs at 283 milliseconds a token, three and a half tokens a second, on both Qualcomm’s stock driver and Mesa Turnip. For scale: every token has to read the full 2.47 gigabytes of weights, and at the bandwidth we measured on this phone that alone takes about 156 milliseconds, so we are at 55 percent of the memory limit. The prompt is processed one token at a time and takes 11.5 seconds; batching it into matrix products is an obvious next step. But the more interesting story is how we got to 283, because the first working version on the stock driver ran at 1,392 milliseconds a token.

## 10. A 4.9× slowdown was one lowering

On the stock driver, the first Llama ran five times slower than on Turnip, and the matrix-vector kernel was three and a half times slower than it should be. To find out whether that was the cost of going through LLVM, we wrote the same kernel in GLSL, Vulkan’s standard shading language, and swapped it into the runtime. GLSL with generic shuffles was just as slow, 45.6 milliseconds, so the route was not the problem. The ShuffleXor instruction was fast, but gave wrong sums, because this driver does not reconverge a subgroup after a loop. The subgroupAdd reduction was fast and correct. LLVM 22 can only emit the generic shuffle, and Mojo’s warp.sum on AMD is six butterfly steps of lane moves. So we taught the retargeter to recognize those six steps and replace them with one native subgroup reduction. The kernel dropped to 14.7 milliseconds, and Llama on the stock driver went from 1,392 to 285 milliseconds a token, with every token still matching.

## 11. Act 3 · How MAX runs a model

Act three is MAX itself. MAX is Modular’s inference platform: you describe a model with its Python graph API, the graph becomes IR in MAX’s own MO dialect, MAX’s graph compiler picks kernels from its Mojo kernel library and compiles them for one specific device, and MAX’s runtime launches them. We built ResNet-18 that way on the Mac, with random weights and batch norm folded into the convolutions. On the CPU it runs in 18 milliseconds an image and matches a NumPy reference to within nine parts in ten million. The first compile took 66 seconds; after that MAX’s cache brings it to one second. On the Mac’s own GPU it failed to compile anything, even a single relu. The likely reason is that the Metal compiler that ships with full Xcode is missing here; later, in the open-source code, we found the error path for exactly that case. And for the Adreno there was simply no target, and no ONNX importer, so a model has to be rewritten in MAX’s graph API.

## 12. Where MAX stopped in 26.7

So where did MAX stop? Four walls. First, there was no code generator for this GPU: the Mojo compiler linked LLVM’s NVIDIA, AMD and Apple backends, and no SPIR-V. Second, MAX’s runtime came as wheels for macOS and Linux hosts, with device backends for CUDA, HIP and Metal, and nothing for Vulkan, OpenCL or Android. Third, the shipped compiler is a closed binary: it would not dump its internal MLIR, so the earliest point we could grab a kernel was the LLVM IR, after Mojo had already committed to an AMD target. Fourth, even if we could reach the phone, MAX’s optimized library kernels are written around NVIDIA tensor cores, AMD matrix cores and asynchronous copies, which have no Vulkan equivalent on this GPU. That is why act two used our own 398-line Vulkan program instead of MAX, and why every kernel went through the retargeter. Then the situation changed.

## 13. ACT 4 · THE COMPILER OPENED UP

Here is where the story turns. On the eighteenth of August 2026, a week after Mojo 1.0, Modular released the source of the Mojo compiler under Apache 2.0 with LLVM exceptions. The same repository, modular/modular, also holds MAX’s graph compiler, its runtime and the kernel library. A clarification, since it came up: there is no Mojo 2.0; the latest release is still 1.2, and the compiler source is on the main branch. More important than the source itself is the design we found in it. Bringing up a new device is meant to go through four extension points: a codegen backend that teaches the compiler to emit code for the device, standard-library hooks for things like thread indices, math and printing, MAX hooks for warp size, barriers and shuffles, and a driver plugin that finds the device and runs work on it. The first three are exactly what a native Adreno target needs.

## 14. What we added: an adreno710 target

So we built the compiler from source and gave it a real target called adreno710. It took three pieces. In the compiler, about 2,100 lines of C++: the target’s identity, which tells the compiler a Vulkan SPIR-V triple is a GPU; a lowering hook that marks kernel entry points; and a backend. Most of the backend is one 1,660-line LLVM pass that does in-process, with full type information, what our Python retargeter did on text: it turns pointer arguments into storage buffers and scalars into a parameter buffer, and rebuilds every address as a buffer and element index. Second, two Mojo plugins, using the extension points we just saw: the standard-library plugin reads thread and block indices from SPIR-V builtins and maps exp, sqrt and friends to native GLSL instructions; the MAX plugin sets 64-lane warps, the barrier and shuffles. Third, one small addition to MAX: a hook that lets a target implement a whole-warp sum natively. The result is one command, and out comes a SPIR-V binary per kernel.

## 15. The native pipeline, inside one compiler

Here is the native pipeline. Everything now happens inside one compiler. Mojo source is parsed and elaborated in Mojo’s own MLIR dialects, KGEN and POP. Because the target is adreno710 from the start, our plugins decide at this stage what a thread index, a barrier or a warp sum becomes: they emit LLVM’s SPIR-V intrinsics directly. Mojo’s normal optimization pipeline runs on the LLVM IR, exactly as it does for NVIDIA and AMD. Then our Vulkan ABI pass reshapes the kernel into a Vulkan entry point, and LLVM 24’s SPIR-V backend, now linked into mojo, writes the binary. Compare with act one: there is no AMD stand-in target any more, no parsing of IR text with regular expressions, no recognizing AMD lane-permute sequences to undo them, and no patching of the finished binary, because LLVM 24 also fixed the barrier bug we patched before. What the target cannot remove are the limits of SPIR-V and the drivers themselves.

## 16. What it took to match the retargeter

A first version that runs is not a version that is fast and exact, and this table is the honest list of what it took. The biggest one was ours: to rebuild an address, the first version computed a 64-bit byte offset and divided it back by four, and since the Adreno emulates 64-bit arithmetic, the naive SGEMM ran 2.6 times slower. Building the element index from the address terms directly, in 32 bits, fixed it. The second: we first used LLVM’s all-memory barrier, which turns out to have device scope; on Adreno that costs twice as much on a shared-memory reduction, so the target now uses a workgroup-scope barrier, like GLSL’s barrier. LLVM 24 still crashes when loop strength reduction rewrites indices, and its machine-level code motion can put an instruction between a structured-control-flow merge and its branch; since the IR is already optimized and the driver compiles the SPIR-V again, codegen simply runs at -O0. The rest were smaller: pointer phis, a missing print hook that surfaced only as a compiler crash, an integer store of float bits, and math functions that were running as polynomials instead of native instructions.

## 17. Native target vs retargeter, same driver

Here is the scorecard: the same eight kernels, the same Turnip driver, the same runner, compiled once through the retargeter and once through the native target. Every kernel passes the full output check both ways. Speed is the same or better. Vector add, warp sum, naive SGEMM and register-tiled SGEMM are level; small kernels like vector add vary by a few tenths of a millisecond from run to run. The two kernels that lean on barriers are faster natively: block sum by more than two times and the fp16 tiles by 15 percent. That is not magic. The retargeter’s barrier also orders global memory, as CUDA’s __syncthreads does; the native barrier orders shared memory only, like GLSL’s barrier, because LLVM has no intrinsic for the in-between variant. For these kernels that is all they need, but it is a semantic difference worth knowing about.

## 18. LLAMA 3.2 1B, EVERY KERNEL FROM MOJO’S OWN COMPILER

And the real test again. We rebuilt all seven Llama kernels with the native target and ran the model with the same weights, the same Vulkan runtime and the same driver, so the only thing that changed is the compiler. Decode runs at 283.6 milliseconds a token, against 285.0 through the retargeter, measured in the same session. All 48 tokens are identical to PyTorch, and the largest logit error is 6.2 times ten to the minus five, exactly what the retargeted build gives. Two things had to be fixed to get here. Attention’s exponential pulled in a debug assertion that needs a print hook, and without one the compiler crashed instead of saying so. And until the math hook mapped exp to the GPU’s native instruction, the logits were three times further from PyTorch. The point of this slide is that the native compiler path is now a complete replacement for the retargeter on Turnip, with no loss of speed or accuracy.

## 19. Act 5 · Is MAX itself portable now?

Act five, and the question everyone asks next: if Mojo now compiles for the Adreno, does MAX run there? Not yet, and it helps to split MAX into layers. The compiler and the standard library: yes, that is the target we just built. MAX’s GPU programming layer, the thread indices, barriers and warp operations that kernels are written with: yes, through the plugins. The runtime, the part that finds a device, allocates its memory and launches kernels, is not ported: it has device backends for CUDA, HIP and Metal and a plugin interface, but nothing for Vulkan, and it is not built for Android at all. The Python API and the model pipelines would additionally need Python on the phone, or MAX’s C API. So today, on the phone, our own small C programs do what the MAX runtime would do. The two layers in the middle, the kernel library and the graph compiler, can be tested without a phone at all. The short answer: the graph compiler runs for a virtual Vulkan device, and all 25 of our test graphs, ResNet-18 included, now compile to valid SPIR-V. Whether they compute the right answers is still open. The next slide has the details.

## 20. Compile test: MAX graphs for vulkan:adreno710

Here is the compile test. MAX has a virtual-device mode for building models on machines without the GPU, so we added a Vulkan entry to it, pointed it at adreno710, and compiled 24 one-operation graphs plus a full ResNet-18, keeping every SPIR-V module and checking each with spirv-val. At first only two graphs compiled. The first round of fixes got us to 16: block-size metadata, a warp-synchronize hook, an Adreno branch to MAX’s plain SIMT matrix multiply, and above all passing tensors by value so that each tensor’s pointer gets its own buffer. The second round took the last nine. Large arguments, such as concat’s list of inputs, arrive in memory, so the backend now reads them field by field. Concat also picks its input buffer at run time, which logical SPIR-V cannot express with a pointer, so the backend reads each candidate and selects the value. Argmax stores structs in shared memory, now done element by element. Conv2d checks pointer alignment, gather has asserts, ResNet zeroes a tile with memset, and an f16 cast works on 8-wide vectors that Vulkan cannot hold; each got a lowering. The last piece was control flow: LLVM’s SPIR-V structurizer expects the tidy code of HLSL and misplaced merge blocks in Mojo’s optimized kernels, so we run LLVM’s general StructurizeCFG first, and we patched one LLVM bug. Now all 25 graphs, 211 kernels including all 74 of ResNet-18, give valid SPIR-V. One caution remains: this is compile only. Nothing has run, so correctness is untested until there is a runtime on the phone.

## 21. What porting MAX’s runtime would take

So what would it take to really run MAX on the phone? Four pieces. First, a Vulkan driver plugin. MAX defines a C interface for new devices, 61 functions covering devices, memory, queues, events and loading kernels; the CUDA, HIP and Metal plugins in the repository are about 2,500 lines each, and our 398-line Llama runtime already does a Vulkan subset of the same job. Second, the runtime libraries have to be built for Android; today the build has no Android toolchain at all. Third, the phone should not run the compiler. MAX can save a compiled model, so the realistic flow is to compile on the Mac for adreno710 and ship the result. Fourth, every operation a model uses has to compile for this target, run correctly, and then be tuned. Compiling is done for our 25 test graphs, ResNet-18 included; running and tuning are open-ended. Items one and two are weeks of engineering, and the tuning is where Modular’s own vendor-specific kernels will need Adreno-specific versions.

## 22. What we learned

Five things to take away. One: Mojo’s LLVM IR turned out to be a workable bridge. With a retargeter we got a real model running on a GPU Mojo never targeted, token for token identical to PyTorch. Two: when it was slow, the cause was almost never SPIR-V as such. It was one specific lowering, the warp sum, which cost a factor of 4.9 on Llama until we fixed it. Three: the drivers decide. Two Vulkan drivers on the same chip disagree about what is fast, and twice about what is correct, so every run checks every output. Four: the native compiler target did not make anything faster than the retargeter at its best, but it made the whole path robust and much simpler, and it lives where the information is. The limits of SPIR-V and the drivers remain. And five: Mojo’s plugin design is real. A new GPU target, with enough fixes to compile every one of our MAX test graphs, ResNet-18 included, was about twenty-six hundred lines of C++ and Mojo. But running MAX models, rather than Mojo kernels, needs the runtime, and that is the long pole.

## 23. What comes next

Where next. First, the 25 MAX graphs compile but have never run: running them on the phone and checking their outputs comes before anything else. On the compiler side, the native target covers Mesa Turnip only. Qualcomm’s stock driver needs a second flavour: SPIR-V for Vulkan 1.1, and the 32-bit narrowing of index math moved into the backend, where it belongs. The same target could also emit OpenCL C, replacing our second retargeter. For Llama, decode is at 55 percent of the bandwidth floor; int4 weights would cut the bytes read by three quarters, fusing small kernels would cut dispatches, and processing the prompt as matrix products would turn eleven seconds into far less. Upstream, the structurizer fix we patched into LLVM belongs in LLVM itself, the strength-reduction crash deserves a small reproducer, and the warp-sum hook and the target itself are natural contributions to Modular once their compiler accepts outside changes, which they have said will be by the end of 2026. The question we started with, can Mojo reach a phone GPU, is answered. The open question is how much of MAX should follow. Thank you.
