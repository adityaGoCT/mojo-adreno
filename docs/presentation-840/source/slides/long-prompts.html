Mojo on the Adreno 840 · 12 · Mojo DeviceContext programs, warm runs · Galaxy S26 Ultra, Android 16 · Llama’s attention: the per-row fallback

How do the models handle long prompts? Here are prefill and decode rates, all on one Galaxy S26 Ultra, every model run as Mojo DeviceContext code with its pipelines already cached. Llama 3.2 1B reads its 431-token prompt at 620 tokens a second with fp16 weights and 670 with 4-bit weights, then generates at 24.5 and 75.3 tokens a second; all 80 generated tokens match PyTorch. On this phone’s Android 16 driver its fused attention kernel does not build, so attention falls back to the per-row kernel. For a fair comparison the ternary Qwen3-8B reads the same passage, which its tokenizer makes 408 tokens: Llama’s 431 include a system header its chat template adds, and both pad to the same 512 rows. Qwen3 reads it in 3.95 seconds, 103 tokens a second, 4.4 times faster than one token at a time, and then generates 21.1 tokens a second, with the same 80 tokens either way. An 8-billion-parameter model reads the prompt about six times slower than a 1-billion one: its projections, 3.6 of the 3.95 seconds, are fp32 matrix products on ternary weights. With a 1000-token prompt Qwen3 reads 106 tokens a second. That prompt first took over 20 seconds, and the attention scores alone 12.2: computing Q times K transposed on cooperative matrices brought them to 0.44, and softmax with P times V moved there too. The plugin now also submits large launches on their own, because 64 of them in one submission outlast the driver’s GPU watchdog. Decode slows as the cache grows: each layer reads 8 kilobytes of fp32 keys and values per position, so a token takes 41 milliseconds after a short prompt, 47.3 after the passage and 58.8 after 1000 tokens. Rewriting the two decode attention kernels, so each cached key is read once for its four query heads and each probability is computed once, halved what that cache costs.
