# Mojo on the Adreno 840: speaker notes

## 1. Mojo on the Adreno 840

This talk is about one GPU and one driver: the Adreno 840 in Qualcomm’s Snapdragon 8 Elite Gen 5, driven by Qualcomm’s own stock Vulkan driver, the one every phone with this chip ships. Mojo does not target phone GPUs officially, so we built Mojo’s compiler from source and gave it a native adreno840 target that writes Vulkan SPIR-V. Then we used the GPU’s matrix units through cooperative matrices, and ran three language models end to end on the phone: Llama 3.2 1B, Bonsai 2 2B with ternary weights, and a ternary Qwen3-8B. Every number in this deck was measured on real phones in two remote device labs, and every model run is checked against a reference.

## 2. The GPU, its driver, and the phones

Here is the setup. The GPU is the Adreno 840, in Qualcomm’s Snapdragon 8 Elite Gen 5, the SM8850. The driver is Qualcomm’s own Vulkan driver, exactly as phones ship it, version 512.842: build 19 on a Galaxy S26 Ultra, on both Android 16 and Android 17, and build 25 on Qualcomm’s SM8850 reference phone. We had no phone on the desk: the S26 Ultra came from Samsung’s Remote Test Lab, bridged to the Mac’s adb through a browser tab, and the reference phone from Qualcomm’s Device Cloud, over an SSH tunnel. What matters for compute is in the table. The driver exposes the matrix units through the standard cooperative-matrix extension, but only for tiles 64 rows tall. Products come in three kinds: fp16 that also sums in fp16, fp32, and int8 into int32. There is no fp16 product with an fp32 sum, which will shape every prompt kernel later. Subgroups are 64 lanes, and a workgroup gets 32 kilobytes of shared memory. Qualcomm’s conversion extension, which we come back to at the end, is on neither build.

## 3. A native adreno840 target in Mojo’s compiler

Mojo’s compiler has been open source since August, so we built it from source and added a target. A Mojo GPU kernel is written exactly as for NVIDIA or AMD. With the flag --target-accelerator adreno840, our target plugins decide what a thread index, a barrier, a warp operation or a matrix tile becomes for this GPU, with 64-lane subgroups. Mojo’s own optimizer runs as usual. Then a Vulkan ABI pass reshapes each kernel into a Vulkan entry point: every pointer argument becomes the next storage buffer, every scalar argument a 64-bit slot of one params buffer, and cooperative-matrix operations get their matrix types. LLVM’s SPIR-V backend, which we patched so Vulkan shaders may use matrix instructions, writes SPIR-V 1.6. What does not exist is MAX’s runtime for Android. So each model here has a small C runner: it loads the weights, creates the pipelines, records every dispatch of a token into one command buffer, and checks the output.

## 4. The matrix units, from Mojo

The matrix units are reached through cooperative matrices: a tile that a whole subgroup loads, multiplies and stores together, while the driver decides which thread holds which element. In Mojo this is a small type, CoopMatrix, with zero, load, multiply-add, cast and store, and the loop on the slide is a complete matrix multiply. Each operation is a marker call; our ABI pass, which already knows which buffer every pointer reaches, rewrites the markers into SPIR-V cooperative-matrix instructions with the right types. On the S26 Ultra, with tiles staged through shared memory, a 2048-cubed multiply runs at 3.7 teraflops in fp16 and 2.5 in fp32. Remember the driver: the fp16 product also sums in fp16, so for long sums we will use fp32 tiles at two thirds of the speed. MAX’s own matmul kernel now takes this path on adreno840 for fp16 and fp32 shapes in multiples of 64: its three test graphs pass on the phone, the fp16 one eight times faster than MAX’s naive kernel.

## 5. What the stock driver needed

Most of the work on this GPU went into its driver. Three behaviours showed up on every build. Half-precision values in shared memory behave as if they were four bytes apart, so only half of an fp16 array is usable; we stage fp16 tiles with matrix loads and stores and halve their offsets. A matrix product whose running sum starts as a tile loaded from memory fails pipeline creation, so every sum starts at zero and a residual is added by a separate kernel. And using exactly all 32 kilobytes of shared memory gives wrong results, so the prompt kernels stay at 16. Then the two builds disagree with each other. The phone came back from the lab on Android 17 with a driver reporting the same version number, and it rejected every matrix pipeline until the compiler wrote its zero tiles as constants instead of building them at run time. On Android 16, our fused attention kernel fails to link, so the runner falls back to per-row attention. And one limit is in the hardware shapes themselves: fp16 products sum only in fp16, so long sums run on fp32 tiles. Each of these either failed outright or silently produced wrong numbers, which is why every run checks every output.

## 6. LLAMA 3.2 1B ON THE ADRENO 840: GENERATING TEXT

The first model is Meta’s Llama 3.2 1B, generating text one token at a time. Seven small Mojo kernels do the work, the matrix-vector products with one 64-lane subgroup per output row, and a C runner records 150 dispatches per token. With fp16 weights, every token reads all 2.47 gigabytes of them, and decode runs at 43 milliseconds a token. Nothing here uses the matrix units: one token is a matrix-vector product, and its speed is set by memory bandwidth. So the lever is bytes. With 4-bit weights, eight to a 32-bit word with one fp16 scale per 64, each token reads about a quarter as much, and decode drops to 13 milliseconds a token. Both formats generate 48 out of 48 tokens identical to PyTorch: the fp16 model against PyTorch in fp32 on the same weights, the 4-bit one against PyTorch with the same dequantized weights.

## 7. LLAMA 3.2 1B: THE PROMPT ON THE MATRIX UNITS

Reading the prompt is where the matrix units pay off. Our runner first pushed the prompt through the decode path, one token at a time, so a 431-token prompt took 17.7 seconds. Processed together, every projection becomes one matrix multiply over all the prompt tokens, and each weight is reused 431 times. We wrote batched kernels for the adreno840 target, and the matrix products run on cooperative matrices in fp32: the fp16 weights are converted while they are staged in shared memory, so the sums keep their accuracy despite the driver’s fp16-only products. The prompt now takes 0.63 seconds, 28 times faster, and all 48 generated tokens are identical to PyTorch, logits within six times ten to the minus five. Most of the time, 556 milliseconds, is the matrix products at about 1.8 teraflops; coalescing the weight copy doubled their speed. Attention is fused too: one subgroup handles 64 prompt tokens of a head, both of its products on the matrix units, 46 milliseconds for all 16 layers. That fused kernel needed the Android 17 build; on Android 16 the runner falls back to per-row attention.

## 8. BONSAI 2 2B: SOMEONE ELSE’S MOJO KERNELS, UNCHANGED

The second model is a different kind of test. Bonsai 2 2B is PrismML’s ternary model: every weight is minus one, zero or one, stored in two bits, and it mixes 18 gated DeltaNet layers, which keep a recurrent state instead of a growing cache, with 6 attention layers. Another developer had already ported it to this same GPU in their own fork of Modular’s repository, through a new OpenCL target. Their GPU kernels are plain Mojo, so we took their kernel file as it is and compiled it with our Vulkan target: all 21 kernels compiled and validated without changing a line. What we wrote is the runtime, their forward pass in C. It generates 80 tokens a second, 12.4 milliseconds a token, and for 16 steps every greedy token matches the exporter’s FP32 reference, with all 248 thousand logits compared. Their OpenCL build reports about 75 a second on a regular S26, so the kernels lose nothing through Vulkan. For the prompt we reused their kernels again: a thin wrapper runs a decode kernel on every prompt row in one dispatch. New are three kernels: the ternary projections as matrix products on cooperative matrices, the attention scores too, and the DeltaNet recurrence as one scan with its state in registers. A 412-token prompt takes 0.87 seconds instead of 5.2, six times faster, and the checked tokens still match.

## 9. TERNARY QWEN3-8B ON THE ADRENO 840

The third model is the largest: PrismML’s Ternary-Bonsai-8B, which is Qwen3-8B with every projection and the output head ternary, 2.19 gigabytes on the GPU. The phone could not reach the internet and the bridge moves about 2.7 megabytes a second, so it was ten minutes of upload before anything ran. Every group of weights turned out to be exactly ternary, so the projections run on the Bonsai port’s packed kernels, unchanged. What Qwen3 needs beyond them is seven small Mojo kernels: RMS norm, the per-head q and k norm with YaRN RoPE and the KV-cache writes in one kernel, attention scores and values, SwiGLU, and the residual add. The RoPE table comes straight from MLX’s own YaRN rope, so positions match the reference exactly. On Qualcomm’s reference phone it generates 25 tokens a second, 40 milliseconds a token, reading the full 2.19 gigabytes each time. For 16 steps every greedy token matches MLX, with all 151,669 logits within 0.008, and asked why the sky is blue it gives the answer on the slide. Its prompt still runs one token at a time, about 38 milliseconds each.

## 10. Three models on one phone GPU

Here are the three models side by side, every row measured on an Adreno 840 with the stock driver and checked against a reference. Llama 3.2 1B generates at 43 milliseconds a token with fp16 weights and 13 with 4-bit weights, and reads a 431-token prompt in about 0.6 seconds either way. Bonsai 2 2B, with ternary weights, is the fastest at 12.4 milliseconds a token and reads a 412-token prompt in 0.87 seconds. The ternary Qwen3-8B generates at 40 milliseconds a token, four times the parameters of Bonsai in a similar number of bytes per parameter. Two patterns run through the table. Generating is bound by memory bandwidth: one token is a matrix-vector product, and its time is how many bytes the weights take, so fewer bits per weight is what helps. Reading a prompt is bound by arithmetic once the tokens are batched, and there the matrix units make it six to 28 times faster than going token by token.

## 11. The same models, run from Mojo

Until now, each model ran from a hand-written C runner. Every model's forward pass now also exists as Mojo host code: a loop of DeviceContext launches of the same kernels, compiled for Android with the kernels inside as SPIR-V. It runs on MAX's own DeviceContext, on MAX's runtime cross-built for Android, and on our Vulkan driver plugin, which implements MAX's device interface on the phone. The times match the runners. Llama 3.2 1B takes 40.6 milliseconds a token with fp16 weights and 12.8 with 4-bit weights, against 43 and 13. Bonsai 2 2B runs the Android port's own model.mojo, unchanged apart from asking for Vulkan, at 13.2 to 13.5 milliseconds, against 12.4 for a runner that records all 721 launches of a token once. The ternary Qwen3-8B takes 39.8 milliseconds against 40. Every row matches its reference token for token. A launch costs 6.5 microseconds because the plugin batches 64 launches into each Vulkan submission. And the phone now downloads each public checkpoint from Hugging Face and converts it itself, into exactly the bytes the Mac's exporter writes, so nothing large crosses adb.

## 12. What VK_QCOM_cooperative_matrix_conversion would add

One thing would change these numbers on the same hardware: Qualcomm’s cooperative-matrix conversion extension, published with Vulkan 1.4.342 in January. It does not replace the KHR extension; it adds four instructions that move data between a thread’s registers and a matrix, so data no longer has to pass through shared memory. For these generative kernels that means four things. First, the weights: one 32-bit word holds sixteen ternary codes, which is exactly one column of an fp16 matrix tile, so each thread could unpack its column in registers and hand it to the matrix unit directly, with no staging and no barrier. Second, and the biggest: the 840 only sums fp16 products in fp16, which is why our prompt kernels use the slower fp32 tiles. With conversion, we pull the fp16 accumulator out every 128 values and add it into fp32 registers, the same precision scheme the decode kernels use, at fp16 speed: our fp16 matrix multiply ran at 3.5 teraflops against 1.8 for the fp32 products in the prefill. Third, fused attention can keep the softmax in registers between its two products. Fourth, ternary weights are exact integers, so int8 products become possible, if the activations can take int8. In estimates, Llama’s 431-token prompt would go from 0.63 to about 0.4 seconds and Bonsai’s from 0.87 to about 0.5. Decode does not change: it is one token at a time and limited by memory bandwidth, so Qwen3-8B stays at 40 milliseconds a token, but a matrix-unit prefill for it becomes worth building. Neither driver we tested offers it yet; the runners now detect it and load the QCOM kernel variants when it appears.

## 13. What the Adreno 840 taught us

Five things to take away. First, on a phone the driver is the platform. The same chip with a driver reporting the same version number rejected our matrix code on Android 17 and failed to link our attention kernel on Android 16, and some quirks gave wrong numbers silently; every run checks every output. Second, the matrix units are for prompts. Generating one token is matrix-vector work, set by how many bytes the weights take, while a batched prompt is matrix work and runs six to 28 times faster. Third, the driver’s fp16-only sums set the ceiling: for accurate prompts we use fp32 tiles at two thirds of the fp16 speed, which is exactly what Qualcomm’s conversion extension would lift. Fourth, Mojo kernels carry over: a kernel file written for another developer’s OpenCL target ran unchanged through our Vulkan target, and its ternary projections then served a second model, Qwen3-8B. Fifth, the runtime was the gap: each model had a hand-written C runner around its kernels. With MAX’s runtime built for Android and our Vulkan driver plugin, every model now also runs as Mojo host code, as fast as its runner.

## 14. What comes next

Three things come next. First, the conversion extension in Mojo itself: today our QCOM kernels are GLSL because LLVM’s SPIR-V backend does not know those instructions; adding them there and to our target would let the same kernels be written in Mojo, and the runners already load them when a driver offers the extension. Second, faster prompts: fp16 products with fp32 sums wherever a driver allows it, and a batched prefill on the matrix units for Qwen3-8B, whose weights are already in the layout our ternary matrix kernel reads. Third, MAX graphs on the phone: Mojo host code already runs there, on MAX’s runtime built for Android and our Vulkan plugin; next is MAX’s graph executor for Android, so that graphs run on the 840 directly instead of through a forward pass written per model. To sum up: with one target flag and the driver every Snapdragon 8 Elite Gen 5 phone ships, three language models run on the Adreno 840 and match their references token for token. Thank you.
