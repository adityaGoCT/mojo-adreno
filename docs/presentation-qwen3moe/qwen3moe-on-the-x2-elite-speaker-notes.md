# Qwen3-30B-A3B on a Snapdragon laptop: speaker notes

## 1. A 30B mixture of experts on a Snapdragon laptop

This is Qwen’s Qwen3-30B-A3B, a mixture-of-experts model: 30.5 billion parameters in 48 layers, each with 128 experts of which a router picks 8 per token, so a token uses 3.3 billion. It runs in int4 on the Adreno X2-90 GPU of a Snapdragon X2 Elite laptop in Qualcomm Device Cloud. The forward pass is Mojo DeviceContext code, the same way SmolVLA and π0 run on that laptop: the program runs on a Mac and drives the laptop’s Vulkan server through our driver plugin. It decodes at 31 to 37 tokens a second. The whole model is 15.75 gigabytes on the GPU, which had to fit inside the GPU’s one 16.8 gigabyte heap. A 404-token prompt is read in 4.31 seconds, 2.8 times faster than a token at a time. And the GPU’s logits are within 1e-4 of transformers’ own Qwen3-MoE layers running on the same weights. The last part of the talk puts one of its layers on the laptop’s Hexagon NPU.

## 2. Fitting it into the GPU’s half of the RAM

The first problem was memory. The X2-90 has one Vulkan heap for compute, 16.82 gigabytes, which is half of the laptop’s RAM; the other heap is protected memory and unusable for this. About 16.0 gigabytes of it was free, and a first layout of 16.7 gigabytes, with a scale per 64 weights everywhere and the embedding on the GPU, failed to allocate its last 0.95 gigabytes. So three changes. The experts, which are 14.5 gigabytes of int4, take one fp16 scale per 128 weights instead of 64. Each group’s scale is the one, between max over 6.5 and max over 9, with the least squared error, rather than max over 7, and that more than pays for the bigger groups: 10.7 percent error on an expert against 11.2 at 64 with max over 7. The 1.24 gigabyte embedding never goes to the GPU: the server copies the row of each token from the file. And the KV cache holds 512 positions. That is 15.75 gigabytes. The weights never cross the network either: the laptop downloads the checkpoint, converts it in four minutes, and the Vulkan server reads it into the GPU from its own disk, 15.65 gigabytes in 4 to 6 seconds, through a new driver request. Through the SSH tunnel to the Mac it would take an hour and a half.

## 3. A token, decoded without asking the host

A token runs entirely on the GPU, and the host never waits for it. Its first request has the Vulkan server copy the token’s embedding row from the file on disk, the token being one the GPU itself wrote: the prompt’s, or the previous step’s argmax. Then 48 layers: attention with int4 projections, QK norm, RoPE and four KV heads shared by 32 query heads; then the router, whose top 8 of 128 experts and their weights stay in GPU memory; the expert kernels read those ids and find their int4 rows by them; and at the end the output head and an argmax that writes the next token into the GPU’s token list. So a whole generation is enqueued at once. It is 531 launches and 1.63 gigabytes of active weights a token. The table is the time of a step, by how many commands the server submits to Vulkan at once. Streamed from the Mac, 8 commands a submission is best: 28 to 32 milliseconds, 31 to 35 tokens a second. Replayed on the laptop itself, with nothing crossing the tunnel, one command a submission is best: 27.2 milliseconds, 36.7 tokens a second, since the GPU runs each launch while the server records the next. That is 55 to 60 gigabytes a second of weights.

## 4. Prefill when each token picks its own experts

Prefill is where a mixture of experts is unusual: the weights a token uses depend on the token, so there is no one weight matrix for the whole prompt. A layer splits in two. Attention has the same weights for every token, so all of the prompt’s tokens go through q, k, v and o at once, as in any batched prefill. Then the router picks each token’s top 8 experts. Before the experts run, the tokens are grouped by expert: each of the 128 experts gets the list of prompt tokens that chose it, about 25 each for a 404-token prompt. Each expert then runs once over its own tokens, a small matrix product with fixed weights, a grouped GEMM. Its weights are read once per layer instead of once per token, and an expert no token chose costs nothing. Finally each token’s eight outputs are added up with its router weights. The kernels give each lane a whole matrix row against 8 tokens, so each int4 word is decoded once for eight tokens; two layouts I tried first were no faster or ten times slower. The result: a 404-token prompt in 4.31 seconds instead of 12.0, and 2.3 to 3.1 times faster from 128 tokens on, over two laptop sessions. Below about 32 tokens most of the GPU sits idle, so short prompts still run a token at a time. The batched logits are within 1.5e-5 of the token-at-a-time path, with the same tokens.

## 5. The Hexagon NPU: fast hardware, static graphs

Then the NPU. The laptop’s Hexagon NPU is the same V81 HTP as the phones’, and we ran one real layer of this model on it in fp16, through ONNX Runtime’s QNN execution provider built for Windows on Arm: attention, the router, and the experts. The catch is that an HTP graph is static. It cannot gather the 8 experts a token chose, so the graph computes all 128 experts for every token and weights them with the router’s top 8, sixteen times the useful work. A token through one layer takes 10.7 to 14 milliseconds, which would be half a second or more a token for 48 layers, against 27 to 32 milliseconds for the whole token on the GPU. A 256-token prefill takes 95 milliseconds a layer, 4.6 seconds for the model, against 2.6 on the GPU; at 128 tokens QNN compiles a worse plan, 10 seconds. The hardware itself is fast: it reads fp16 weights at about 100 gigabytes a second, faster than our GPU kernels, and runs 3.4 teraflops of fp16 matrix work. If it could read only the 8 chosen experts, a layer would take under a millisecond. It is accurate too, once the QK norms are written as L2 normalizations, because QNN refuses its RmsNorm on heads of 128. But the whole model in fp16 is 61 gigabytes, far more than the laptop has, so on the NPU it would need the quantized w4a16 path.

## 6. Checked, and what comes next

Everything is checked. The reference is transformers’ own Qwen3-MoE layers, run a layer at a time on the laptop, since the bf16 model fits neither the laptop nor the Mac at once. On the same int4 weights the GPU’s logits are within 1e-4 at every position, and every greedy token matches, 31 of 31 and 95 of 95 on two prompts. Against the original bf16 model, 31 of 32 greedy choices agree, and the one difference comes after the answer has ended. Asked why the sky is blue, it answers in two correct sentences. What comes next: the prefill’s products still run on the plain ALUs, eight tokens a row, and the cooperative-matrix units would read a prompt several times faster. The RMSNorms, router and top-8 are a quarter of a decode step as 192 small launches, waiting to be fused. The NPU would become worthwhile if its graphs could read only the chosen experts, or if it took the dense attention while the GPU takes the experts. And better int4 rounding, GPTQ or AWQ style, would fit the same storage and kernels.
