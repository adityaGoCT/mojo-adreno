Two ways onto the chip

GPU: Adreno 840, Adreno X2-90

  • Mojo DeviceContext kernels, SPIR-V from the fork’s adreno840 target, through Vulkan.
  • Decided at run time: a kernel reads the router’s expert ids; a prompt of any length.
  • int4 and int8 weights, unpacked inside the kernels.
  • Prefill on KHR cooperative matrices (fp32, 64 × 64 × 8).

NPU: Hexagon HTP V81

  • fp16 ONNX graphs through ONNX Runtime’s QNN execution provider (ORT 1.29 + QNN 2.42 from Maven Central).
  • Compiled once, on the device, for fixed shapes: 448 rows for Llama (201 s), 832 for π0 (18.5 min).
  • Compiled contexts load at each process start: 1.9–2.4 s (Llama).
  • Quantized weights only per output channel (w8a16, w4a16).

Two routes onto the same chip. On the GPU, everything is Mojo: DeviceContext programs whose kernels the fork’s adreno840 target compiles to SPIR-V, run through Vulkan, on the phone’s Adreno 840 and the laptop’s X2-90. Because the kernels run whatever the host enqueues, they can make decisions at run time: an expert kernel reads the ids the router wrote, and a prompt can be any length. Weights are int4 or int8, unpacked inside the kernels, and prefill uses the cooperative-matrix units. The NPU route is different. A retail phone has no Qualcomm SDK, but ONNX Runtime’s QNN execution provider and QNN’s HTP libraries are public on Maven Central. We write fp16 ONNX graphs, and the phone compiles them for the HTP once, for fixed shapes: Llama’s graphs take 448 rows and 201 seconds to compile; π0’s take 832 rows and 18.5 minutes. Each process then loads the compiled contexts, about 2 seconds for Llama. Quantized weights work only per output channel, as we will see. The two meet in a handoff: the NPU prefills the prompt and the GPU decodes from its K/V cache. Each part’s K/V is copied while the NPU runs the next part, so only 0.8 to 2 milliseconds remain after the last one.
