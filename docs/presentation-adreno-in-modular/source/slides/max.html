MAX’s device plugin interface: about 60 C functions, now on Vulkan (mojo-adreno driver/) · runtime: --config=android-arm64

The next step is MAX itself, and much of the way is now done. All 26 of our MAX test graphs, ResNet-18 included, compile for a Vulkan Adreno 840 device; MAX’s matmul picks a matrix-unit kernel there, and its three test graphs pass on the phone. And MAX’s DeviceContext now runs on the phone: MAX’s runtime is cross-built for Android, and our driver plugin implements MAX’s device interface, about 60 C functions, on Vulkan. That is what the Mojo host code of the last slides runs on. Bringing the whole of MAX to the phone still has clear advantages. A model would be defined once, as the same MAX graph that runs on NVIDIA and AMD, instead of a forward pass written per model. The graph compiler would fuse operations and plan memory, cutting the 615 to 721 launches a token our forward passes make today. MAX’s pipelines bring the tokenizer, sampling, KV cache management and serving. And models can be compiled on a Mac and shipped compiled, so the phone never runs the compiler. The challenges are concrete. MAX’s graph executor still needs its Android build, on top of the Mojo runtime and the device plugin that now have theirs. The kernels have to fit Adreno’s shapes: 64-row matrix tiles, fp16 products that sum only in fp16, 32 kilobytes of shared memory. The ternary and 4-bit formats that make models small are custom kernels today and would become MAX custom ops. Driver builds behave differently, so compiled graphs need checking on the device. And phone memory is shared and small, so weights must be mapped once and compilation kept off the phone.
