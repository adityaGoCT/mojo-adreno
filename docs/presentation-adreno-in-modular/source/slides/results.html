Decode: memory bandwidth

One token is a matrix-vector product: its time is the bytes of weights read. Fewer bits per weight took Llama from 43 to 13 ms.

Prefill: the matrix units

All prompt tokens at once reuse every weight: fp32 cooperative-matrix products at about 1.8 TFLOP/s, 6 to 28 times faster.

Prompts: Llama 431 tokens, Bonsai 412, Qwen3 19–23 · Llama and Bonsai decode: Galaxy S26 Ultra · the rest: SM8850 reference phone

Here are the results for every model, all on an Adreno 840 with Qualcomm’s stock driver, and all checked against a reference. Decode first. Llama 3.2 1B generates at 43 milliseconds a token with fp16 weights, 23 tokens a second, and at 13 milliseconds with 4-bit weights, about 75 a second. Bonsai 2 2B, with ternary weights, is the fastest at 12.4 milliseconds, 80 tokens a second. The ternary Qwen3-8B, the largest model, generates 25 tokens a second. Then prefill, reading the prompt, as a rate in prompt tokens per second. Token by token, Llama reads 24 tokens a second, 17.7 seconds for a 431-token prompt; batched on the matrix units it reads 684 tokens a second, 0.63 seconds, 28 times faster, and 695 a second with 4-bit weights. Bonsai goes from 80 tokens a second token by token to 474 batched, six times faster, for a 412-token prompt in 0.87 seconds. Qwen3-8B still reads its prompt one token at a time, about 27 tokens a second; its batched prefill is the next step. Note that token by token, prefill runs at the decode rate: it is the same path. Two rules explain the table. Decode is bound by memory bandwidth: one token is a matrix-vector product, so its time is the bytes the weights take. Prefill is bound by arithmetic once the tokens are batched, and there the matrix units pay off. Every row matches its reference token for token: PyTorch for Llama, MLX in FP32 for the ternary models.
