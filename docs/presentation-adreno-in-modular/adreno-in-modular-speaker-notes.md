# Adreno in Modular: speaker notes

## 1. Adreno as a native backend in Modular’s compiler

Mojo officially targets NVIDIA, AMD and Apple GPUs. Since Modular open-sourced the compiler, we added Adreno as a native backend, in five pieces. First, the target itself: the accelerator name adreno840 selects Vulkan SPIR-V output with 64-lane subgroups and enables cooperative matrices, the GPU’s matrix units. Second, the GPU intrinsics: when a kernel asks for its thread index, a barrier, a lane shuffle, a warp reduction or a math function, the lowering emits the matching SPIR-V builtin. Third, the Vulkan kernel ABI pass reshapes each kernel into a Vulkan entry point: every pointer argument becomes the next storage buffer, every scalar a slot in one params buffer; it also structures control flow the way Vulkan requires and gives cooperative matrices their types. Fourth, LLVM’s SPIR-V backend, linked into mojo, writes the binary, with two small patches. Fifth, MAX: the CoopMatrix type for kernel authors, MAX’s matmul picking a matrix-unit kernel on the 840, and MAX graphs compiling for a Vulkan Adreno device. All of it is built on Modular’s open-source compiler, and the result is one flag: target adreno840, get a Vulkan shader per kernel that runs on Qualcomm’s stock driver.

## 2. A Mojo kernel, and the SPIR-V it becomes

Here is what the backend produces, from real kernels. The first row is subgroup code. In Mojo you write shuffle_xor to exchange a value with the lane whose index differs in one bit, and warp_sum to add a value across the whole subgroup, 64 lanes on the Adreno. In the SPIR-V, the shuffle becomes the lane id read from the SubgroupLocalInvocationId builtin, an exclusive-or with the mask, and a GroupNonUniformShuffle at subgroup scope; the warp sum becomes a single GroupNonUniformFAdd reduction. The second row is a cooperative matrix, the matrix units. A, B and Acc are CoopMatrix types: a 64 by 8 tile of A, an 8 by 64 tile of B, a 64 by 64 accumulator, all fp32. In the SPIR-V each becomes an OpTypeCooperativeMatrixKHR, the zero accumulator a constant, the loads from shared memory carry their layout, row-major for A and column-major for B, and their stride, the multiply-add is one instruction, and the store writes the tile to the output buffer. The listings are spirv-dis output of our compiled kernels with the ids renamed so they can be read; around them, every pointer argument of the kernel is a storage buffer at the next binding, and every scalar argument a slot of one params buffer.

## 3. Mojo kernels, run by a small C program

This is how a model actually runs. The kernels are plain Mojo GPU functions, written as for any GPU. The compiler, with the adreno840 target, turns each into its own SPIR-V file, and every file is checked with spirv-val. On the Mac, an exporter writes the weights in exactly the layout the kernels read, packed 4-bit or ternary where the model is, together with reference logits from PyTorch or MLX. MAX’s runtime does not exist on Android, so the part that runs the model is a small C program, built with the Android NDK, that talks to Vulkan directly through the phone’s own libvulkan. At start-up it loads every SPIR-V file into a pipeline, copies the weights into GPU buffers, and records every dispatch of one token into a single command buffer, once. Then, per token, it only writes the token id and the position into the params buffer, submits that command buffer, waits, and takes the argmax on the CPU. The runner needs to know nothing about Mojo: a kernel’s pointer arguments are its buffer bindings in order, and its scalar arguments are slots of one params buffer. The table gives the sizes: Llama 3.2 1B is nine Mojo kernels plus eight for its prefill, with a 563-line runner and 150 dispatches a token; Bonsai 2 2B is the 21 kernels of another developer’s port plus 20 for prefill, 747 lines and 721 dispatches; the ternary Qwen3-8B adds seven kernels to three of Bonsai’s, with a 414-line runner and 615 dispatches a token.

## 4. Prefill and decode on the Adreno 840

Here are the results for every model, all on an Adreno 840 with Qualcomm’s stock driver, and all checked against a reference. Decode first. Llama 3.2 1B generates at 43 milliseconds a token with fp16 weights, 23 tokens a second, and at 13 milliseconds with 4-bit weights, about 75 a second. Bonsai 2 2B, with ternary weights, is the fastest at 12.4 milliseconds, 80 tokens a second. The ternary Qwen3-8B, the largest model, generates 25 tokens a second. Then prefill, reading the prompt, as a rate in prompt tokens per second. Token by token, Llama reads 24 tokens a second, 17.7 seconds for a 431-token prompt; batched on the matrix units it reads 684 tokens a second, 0.63 seconds, 28 times faster, and 695 a second with 4-bit weights. Bonsai goes from 80 tokens a second token by token to 474 batched, six times faster, for a 412-token prompt in 0.87 seconds. Qwen3-8B still reads its prompt one token at a time, about 27 tokens a second; its batched prefill is the next step. Note that token by token, prefill runs at the decode rate: it is the same path. Two rules explain the table. Decode is bound by memory bandwidth: one token is a matrix-vector product, so its time is the bytes the weights take. Prefill is bound by arithmetic once the tokens are batched, and there the matrix units pay off. Every row matches its reference token for token: PyTorch for Llama, MLX in FP32 for the ternary models.

## 5. Next: MAX itself on the Adreno

The next step is MAX itself, and part of the way is already done. All 26 of our MAX test graphs, ResNet-18 included, compile for a Vulkan Adreno 840 device; MAX’s matmul picks a matrix-unit kernel there, and its three test graphs pass on the phone; and MAX has already driven an Adreno through a remote device, MAX on the Mac and Vulkan on the phone. Bringing the whole of MAX to the phone has clear advantages. A model would be defined once, as the same MAX graph that runs on NVIDIA and AMD, instead of a hand-written C runner per model. The graph compiler would fuse operations and plan memory, cutting the 615 to 721 dispatches a token our runners record today. MAX’s pipelines bring the tokenizer, sampling, KV cache management and serving. And models can be compiled on a Mac and shipped compiled, so the phone never runs the compiler. The challenges are just as concrete. MAX’s runtime has no Android build, and its device plugin, about 60 C functions, needs a Vulkan implementation on the phone. The kernels have to fit Adreno’s shapes: 64-row matrix tiles, fp16 products that sum only in fp16, 32 kilobytes of shared memory. The ternary and 4-bit formats that make models small are custom kernels today and would become MAX custom ops. Driver builds behave differently, so compiled graphs need checking on the device. And phone memory is shared and small, so weights must be mapped once and compilation kept off the phone.
