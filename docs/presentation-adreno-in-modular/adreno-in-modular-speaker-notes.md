# Adreno in Modular: speaker notes

## 1. Adreno as a native backend in Modular’s compiler

Mojo officially targets NVIDIA, AMD and Apple GPUs. Since Modular open-sourced the compiler, we added Adreno as a native backend, in five pieces. First, the target itself: the accelerator name adreno840 selects Vulkan SPIR-V output with 64-lane subgroups and enables cooperative matrices, the GPU’s matrix units. Second, the GPU intrinsics: when a kernel asks for its thread index, a barrier, a lane shuffle, a warp reduction or a math function, the lowering emits the matching SPIR-V builtin. Third, the Vulkan kernel ABI pass reshapes each kernel into a Vulkan entry point: every pointer argument becomes the next storage buffer, every scalar a slot in one params buffer; it also structures control flow the way Vulkan requires and gives cooperative matrices their types. Fourth, LLVM’s SPIR-V backend, linked into mojo, writes the binary, with two small patches. Fifth, MAX: the CoopMatrix type for kernel authors, MAX’s matmul picking a matrix-unit kernel on the 840, and MAX graphs compiling for a Vulkan Adreno device. All of it is built on Modular’s open-source compiler, and the result is one flag: target adreno840, get a Vulkan shader per kernel that runs on Qualcomm’s stock driver.

## 2. A Mojo kernel, and the SPIR-V it becomes

Here is what the backend produces, from real kernels. The first row is subgroup code. In Mojo you write shuffle_xor to exchange a value with the lane whose index differs in one bit, and warp_sum to add a value across the whole subgroup, 64 lanes on the Adreno. In the SPIR-V, the shuffle becomes the lane id read from the SubgroupLocalInvocationId builtin, an exclusive-or with the mask, and a GroupNonUniformShuffle at subgroup scope; the warp sum becomes a single GroupNonUniformFAdd reduction. The second row is a cooperative matrix, the matrix units. A, B and Acc are CoopMatrix types: a 64 by 8 tile of A, an 8 by 64 tile of B, a 64 by 64 accumulator, all fp32. In the SPIR-V each becomes an OpTypeCooperativeMatrixKHR, the zero accumulator a constant, the loads from shared memory carry their layout, row-major for A and column-major for B, and their stride, the multiply-add is one instruction, and the store writes the tile to the output buffer. The listings are spirv-dis output of our compiled kernels with the ids renamed so they can be read; around them, every pointer argument of the kernel is a storage buffer at the next binding, and every scalar argument a slot of one params buffer.

## 3. Mojo kernels, run by Mojo host code

This is how a model runs now, entirely in Mojo. The kernels are plain Mojo GPU functions, as before, and the forward pass is Mojo too: a loop of DeviceContext launches, the same code you would write for an NVIDIA or AMD GPU. The compiler builds it for Android: arm64 host code with every kernel inside as adreno840 SPIR-V. The weights never cross adb: the phone downloads each public checkpoint from Hugging Face and converts it itself, byte for byte what the Mac's exporter writes. At run time the program uses MAX's own DeviceContext, the HAL one, which is plain Mojo and loads a driver plugin. That plugin is ours: it implements MAX's driver C interface, about 60 functions, on Vulkan, and turns each launch's arguments into buffer bindings and params as the launch descriptions in the SPIR-V say. MAX's runtime itself is cross-built for Android with the configuration of the Android OpenCL port. The table compares the C runners this replaces. Llama's forward pass is 150 lines of Mojo instead of a 563-line C runner, Qwen3's 165 instead of 414, and Bonsai runs the port's own model.mojo, unchanged apart from asking for Vulkan instead of OpenCL. Speed is the same: a launch costs 6.5 microseconds because the plugin batches 64 launches into each Vulkan submission, so Llama decodes at 24.7 tokens a second against 23 for its C runner, Qwen3-8B at 25.1 against 25. Only Bonsai, with 721 small launches a token, gives up a few percent: 74 to 76 against 80. Llama's batched prefill runs from Mojo as well, its matrix kernels launched per layer, and reads a 431-token prompt in 0.65 seconds, against 0.62 for its C runner.

## 4. Prefill and decode on the Adreno 840

Here are the results for every model, all on an Adreno 840 with Qualcomm’s stock driver, and all checked against a reference. Decode now has two columns: the Mojo host code, where the forward pass is Mojo DeviceContext code running on the phone, and the C runners it replaces. Llama 3.2 1B generates 24.7 tokens a second with fp16 weights through Mojo, against 23 for its C runner, and 78.1 with 4-bit weights against 75. Bonsai 2 2B runs the Android port's own model.mojo at 74 to 76 tokens a second; its C runner, which records a token's 721 dispatches once, reaches 80. The ternary Qwen3-8B, the largest model, generates 25.1 tokens a second through Mojo and 25 through C. So launching each kernel from Mojo costs nothing measurable: decode is bound by memory bandwidth, one token is a matrix-vector product, and its time is the bytes the weights take. Fewer bits per weight is what took Llama from 43 to 13 milliseconds. Prefill, reading the prompt, runs batched on the matrix units: Llama reads 684 tokens a second, 0.63 seconds for 431 tokens, 28 times faster than one token at a time; Bonsai goes from 80 to 474 tokens a second. Llama's batched prefill now runs from Mojo too, as fast as its C runner: the same 431-token prompt in 0.65 seconds with fp16 weights and 0.59 with 4-bit weights, every generated token still matching PyTorch. Qwen3-8B still reads its prompt one token at a time. Every row matches its reference token for token, through Mojo and through C alike: PyTorch for Llama, MLX in FP32 for the ternary models.

## 5. Next: MAX itself on the Adreno

The next step is MAX itself, and much of the way is now done. All 26 of our MAX test graphs, ResNet-18 included, compile for a Vulkan Adreno 840 device; MAX’s matmul picks a matrix-unit kernel there, and its three test graphs pass on the phone. And MAX’s DeviceContext now runs on the phone: MAX’s runtime is cross-built for Android, and our driver plugin implements MAX’s device interface, about 60 C functions, on Vulkan. That is what the Mojo host code of the last slides runs on. Bringing the whole of MAX to the phone still has clear advantages. A model would be defined once, as the same MAX graph that runs on NVIDIA and AMD, instead of a forward pass written per model. The graph compiler would fuse operations and plan memory, cutting the 615 to 721 launches a token our forward passes make today. MAX’s pipelines bring the tokenizer, sampling, KV cache management and serving. And models can be compiled on a Mac and shipped compiled, so the phone never runs the compiler. The challenges are concrete. MAX’s graph executor still needs its Android build, on top of the Mojo runtime and the device plugin that now have theirs. The kernels have to fit Adreno’s shapes: 64-row matrix tiles, fp16 products that sum only in fp16, 32 kilobytes of shared memory. The ternary and 4-bit formats that make models small are custom kernels today and would become MAX custom ops. Driver builds behave differently, so compiled graphs need checking on the device. And phone memory is shared and small, so weights must be mapped once and compilation kept off the phone.
