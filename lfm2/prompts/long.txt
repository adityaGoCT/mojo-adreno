Mobile graphics processors began as fixed-function blocks that could only draw textured triangles for games and user interfaces. Over the following fifteen years they became general programmable processors. Vendors added unified shader cores, then compute shaders, then support for half-precision arithmetic, because neural networks and image filters tolerate lower precision and run twice as fast with it. Memory bandwidth, however, grew far more slowly than arithmetic throughput. A phone shares one pool of memory between the CPU, the GPU, the display and the camera, and it must stay within a few watts of power, so every byte moved from memory costs both time and battery.

This imbalance shapes how language models run on phones. Generating text one token at a time is limited by memory bandwidth: every new token needs every weight of the model once, but performs only two arithmetic operations per weight. Reading the prompt is different. When all prompt tokens are processed together, each weight is reused for every token, so the work becomes a matrix multiplication whose cost is dominated by arithmetic rather than memory traffic. That is why recent mobile GPUs add matrix units, small blocks that multiply tiles of numbers in a single instruction, and why graphics APIs added cooperative matrices, which let a group of threads load, multiply and store such tiles together while the driver decides how the elements are spread across the threads.

Using these units well still takes care. Tiles of the inputs must be staged in fast on-chip shared memory so that several groups of threads can reuse them, the shapes must match what the hardware supports, and the accumulation precision must be chosen so that long sums do not lose accuracy. When this is done, reading a long prompt can become many times faster than generating the same number of tokens, which shortens the wait before a phone assistant starts to answer.
